## Parâmetros técnicos implementados

Senha nova: 15–128 pontos de código Unicode, sem truncar, alterar espaços ou impor composição arbitrária. Login aceita a mesma contagem máxima, incluindo Unicode. Não são valores atribuídos ao PDF: são validação técnica deste incremento. scrypt v1 N=131072/r=8/p=1/salt aleatório 16 bytes/derivação 64 bytes/maxmem 256 MiB ratificados; duas derivações simultâneas e fila de até 16 para conter memória. Custo aferido pelos testes, sem meta de latência inventada. Conta desconhecida executa a mesma KDF. Tokens opacos usam 32 bytes aleatórios; SHA-256 separado por propósito no banco. Histórico de hashes de refresh mantém identificação de reutilização dentro da sessão, nunca tokens em claro; prazo absoluto não é estendido. Cliente deve coordenar uma renovação de cada vez; reutilização concorrente revoga a sessão conforme decisão ratificada.

Padrões configuráveis: AUTH_LOGIN_ACCOUNT=5 e AUTH_LOGIN_IP=20 por 15 minutos; AUTH_REGISTER_IP=10 por hora; AUTH_REFRESH_IP=120 por 15 minutos. Valores inteiros de 1 a 10000; zero não desativa proteção. Contam tentativas admitidas, inclusive login válido. Persistência por registros de auditoria com escopos pseudonimizados e janelas, sem e-mail/IP em claro nesses contadores; não é afirmação de anonimização irreversível. Não confiar em X-Forwarded-For/Proto de cliente; trust proxy não é habilitado. Nenhum serviço externo/cobrança real usado.

WEB_ORIGIN deve ser uma origem HTTPS canônica e exata, padrão local `https://localhost:5173`. Para web, enviar Origin nas mutações e X-CSRF-Token igual ao cookie __Host-garimpo-csrf; cookies de acesso/refresh são HttpOnly. Para mobile, enviar X-Garimpo-Client: mobile, Authorization: Bearer no acesso e refreshToken no corpo de refresh/logout; cookies simultâneos são negados. Administração exige o canal web. Cabeçalho mobile seleciona transporte de credencial, não concede papel nem comprova aparelho. Toda permissão e estado são revalidados no banco. /health continua probe interna HTTP sem credencial; rotas de contas negam HTTP mesmo com X-Forwarded-Proto forjado.

## Comandos locais

Carregar ambiente conforme tests/core/README.md. `npm run db:migrate` aplica as migrations à base dev explicitamente configurada; nunca migrate reset. Para iniciar API com contas: carregar DATABASE_URL e configurar TLS_CERT_PATH/TLS_KEY_PATH com certificado confiável ao cliente; `npm run dev:api`. Nenhuma geração ou confiança de certificado no sistema do usuário é realizada automaticamente. O teste local usa sua própria confiança explícita, sem modificar repositório de certificados Windows/Android.

Primeiro ADMIN: somente após a migration, usar variáveis BOOTSTRAP_ADMIN_NAME/BOOTSTRAP_ADMIN_EMAIL e senha recebida com `read -r -s -p 'Senha: ' BOOTSTRAP_ADMIN_PASSWORD` no Ubuntu; exportar a variável sem escrever o valor literal no histórico. Executar `npm run bootstrap:admin` e depois `unset BOOTSTRAP_ADMIN_PASSWORD`. Não colocar senha em argumento, código ou commit. Comando exige DATABASE_URL e senha não padrão, valida dados e recusa se já existir qualquer conta STAFF; recuperação administrativa posterior exige decisão operacional explícita. Nenhum endpoint público de bootstrap existe.
